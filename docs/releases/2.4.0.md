# settlemaker 2.4.0 — village streets, bridges and biome homes

This release replaces preset village road layouts with a shared street network
that grows with housing demand. FMG approaches keep their measured bearings,
then join town, local and footpath streets. Small roadside hamlets can retain a
major through road. Greens follow their connected routes, landmarks use useful
frontage, and vegetation fills spare ground according to biome.

River crossings use separate timber decks; ordinary road paint stays out of
water. Tundra houses, huts and large homes now use the native snowy artwork.

## FMG adapter handoff

The authoritative contract is [url-api.md](../url-api.md). The FMG agent should:

1. Send one approach record per measured side, preserving each bearing and its
   actual class. Keep close bearings and reuse a stable `route_id` when two sides
   belong to the same world route. `through: true` never invents another side.
2. Send one of `royal`, `main`, `market`, `town`, `local`, `trail`, `footpath`
   in `kind`. Group-only adapters can retain the documented legacy aliases.
   Do not put sea, air or trade-network links into village land approaches.
3. Send filled coast, lake and river polygons in `coastlineGeometry`. Village
   coordinates use metres relative to the burg, x east and y south. Preserve
   both river banks, width and bends; extend water beyond the tile. The
   `followsRiver` hint alone cannot draw water. Portless coasts still need water.
4. Send the actual biome in `burg.biome`; `villageTheme` alone changes colours
   and materials, not the dwelling family. Existing FMG biome names are accepted.
5. Preserve all seven explicit burg flags and the seed. Send `roadBearings: []`
   for a known routeless burg. Use the compressed `i=` payload for real adapters.
6. Validate multi-approach, bent-through, close-bearing, brook, coast and tundra
   examples. The local galleries are synthetic fixtures, not captured FMG data.

No FMG source changes are included in this release. Village street GeoJSON
exposes `route_role`, `route_ids`, surface widths/clips and bridge deck geometry;
custom renderers should follow the [village output notes](../schema-v3.md#village-road-cross-sections).

## Compatibility and rollout

- Package and output `settlemaker_version`: **2.4.0**.
- URL envelope remains **v1**, GeoJSON remains **schema 4**. New output fields
  are additive; the population boundary remains 1,000 / 1,001.
- Layouts and generated feature IDs change from 2.3.0. Invalidate generated-tile
  caches or include the generator version/revision in cache keys.
- Older callers relying on an invented +180° exit must send the actual second
  approach. Existing bare bearings and legacy kinds remain accepted.
- Wide-river bridge design remains outside this release.
- settlemaker-web must pin the release commit in its `settlemaker/` submodule.
  Its existing build emits `/lib/settlemaker.js`; no FMG payload-version change
  or site import-path change is required. Publishing the web master pin triggers
  the site's configured Netlify build. Revert that pin commit to roll back.

## Validation

The final generator implementation passed 1,296 tests in 124 files, TypeScript
compilation, script type checks and the browser bundle build. All 112 fixed and
held-out village fixtures house their populations with no building-access
failures. Both city control drawings remain unchanged. Brook population 300
seed 3 has seven bridge crossings, longest 6.48 m; every building in tundra
population 300 seed 2 uses tundra artwork. The release bump also passed all
100 URL, codec, output-version and generation checks in the seven relevant
test files, plus a fresh library build and type checks.
