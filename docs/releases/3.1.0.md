# 3.1.0 — physical planning, shared appearance and retained rendering

The npm package and hosted website have separate release cycles;
publishing the package does not establish
which engine a deployed renderer uses.

## Planning and population

The opt-in physical planner shares village and city development, landscape,
rendering and export through a `SettlementModel` in local metres. Pass
`development: { preset: 'village' | 'city' }` to `generateSettlement`, or call
`planSettlement` directly. The result has `kind: 'planned'`; existing calls
without `development` retain their original result types and coordinates.

Development options expose enclosed-core population, ordinary household capacity
and an optional rural resident target. Resident accounts report requested,
available, assigned and unassigned population, including inside/outside walls
and urban/rural splits. Bounded planning retries add real housing supply;
shortfalls remain visible instead of being hidden by inflated capacity.

City blocks combine attached street houses with appropriately sized tenements,
more detached outskirts and reserved public greens. Rural farmsteads and small
hamlets connect to the road network, with cultivated ground fitted around their
buildings and tracks. See [shared settlement planning](../settlement-planning.md)
for options, constraints and the separate physical export contract.

## Appearance and artwork

Original planners now accept `burg.engine` or `options.engine` as `auto`,
`village` or `city`, independently of population. Automatic selection still uses
the existing 1,000-person village boundary. Named `theme` and partial `style`
options apply shared colours to both planners while preserving their geometry;
biomes and skins retain their distinct generation and artwork roles.

City improvements include more reliable glyph fitting in awkward lots, usable
frontage around civic courts, denser enclosed neighbourhoods and properly sized
compound sites. Compound roofs can reference several real building IDs without
merging their census or exported footprints. Inn and courtyard artwork has finer
roof details at its intended scale. Wells have consistent physical size and
shorter low-object shadows. Parks use biome-appropriate shade trees in groves,
with clear paths and fortification clearance; repeated decorative ground bumps
have been removed.

See [appearance and engine selection](../appearance.md) and the
[generated gallery](../gallery.md).

## Rendering and integration

`createSettlementSession` retains a generated model for repeated viewport and
appearance renders. `renderView` uses indexed scene queries, display-scale detail
and conservative artwork bounds. Offscreen wall segments and motifs are culled
without restarting motif spacing. Legacy villages retain a full-SVG rendering
fallback. `renderFull` provides the complete export independently of viewport
state, while `exportGeoJson` defers export work until requested.

Session metadata identifies the planner, seed, original bounds, coordinate units,
scale provenance and revisions. `BUILD_INFO` supports version checks between a
page and its worker. The API remains synchronous: applications should use a
worker for expensive generation and rendering. Browser tile caches, atlas
batching and navigation belong to the separately deployed website, not an
asynchronous npm generator API. See the [API reference](../api.md#retained-rendering-sessions).

## Upgrade and reproducibility

**The same seed can produce a different layout or SVG after this upgrade.**
Housing allocation, compound sites, countryside placement, civic geometry and
vegetation have changed. Existing feature IDs must not be treated as stable
across generator versions. Record the complete input, resolved seed, package
version and skin/rendering options, and invalidate cached maps when upgrading.

Existing contract versions remain compatible: legacy GeoJSON schema 4, Scene 2,
URL envelope 1, skin format 1 and measured-water format 1. Added scene fields,
such as compound `buildingIds`, supplement existing identities. The new physical
model is version 1 and its GeoJSON uses the separate
`settlemaker/physical-plan` schema version 1; its metre coordinates must not be
interpreted as legacy city mesh coordinates. The worker protocol is version 1.

Update a URL renderer before exposing `engine` or shared-theme controls to
embedders. Existing URLs that omit the new controls keep automatic planner
selection. Read the [contract version table](../README.md#contract-versions)
and [URL adapter guide](../url-api.md) when updating an integration.
